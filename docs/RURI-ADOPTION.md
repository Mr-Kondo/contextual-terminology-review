# Ruri検索の採否判断（2026-10-17、検証の途中結果）

結論は「**この証拠の範囲では、310mなら任意の補助として使える可能性がある。70mは基準に届かなかった**」。**決定（利用者、2026-10-17）: 既定モデルを `cl-nagoya/ruri-v3-310m`（revision `18b60fb8…`、既定のときだけ版を固定）にした。** 実データでの確認は残っており、Ruriは引き続き任意の補助である。70mは `--model cl-nagoya/ruri-v3-70m` で指定できる。

## 何を比べたか

用語の一致検索では見つからない言い方（表記ゆれ・言い換え）を、用語集から拾えるか。

- 比較対象: 一致検索（現行）／文字2-gram（標準ライブラリのみ。依存なしの代替案）／Ruri v3 70m（現行の既定）／Ruri v3 310m／一致＋補助（一致を先頭に、閾値を超えた補助の結果で埋める）
- 課題セット: [tools/data/ruri-adoption-set.json](../tools/data/ruri-adoption-set.json)。架空の用語集40語、課題80件（そのまま含む16・表記ゆれ20・言い換え24・無関係20）。偶数番がdev（閾値の決定だけに使用）、奇数番がtest（報告の主）
- 採点: 正解のどれかが上位3件に入れば命中。無関係な文には『何も返さない』が正解
- 閾値: devの無関係課題の1位得点の最大値。これを**超えた**結果だけを返す。positive側の成績は閾値の決定に使っていない
- 採否基準（実行前に固定。`tools/bench_ruri_adoption.py` の冒頭）: testの表記ゆれ＋言い換え（n=22）で、Ruriの閾値つきhit@3が**0.60以上**、かつ文字2-gramより**0.15以上高く**、testの無関係課題の誤検出が**0.20以下**

|---|---|---|---|---|

- 17/22（0.77）の95%区間（Wilson）は0.57〜0.90。基準Aの0.60は区間の下限を下回るため、基準は点推定で満たしただけ。
- 一致検索の無関係課題の誤検出は報告の表には出していない（閾値の概念が無いため）。課題セットの検査（`tests/test_ruri_bench_set.py`）で、無関係な20件に一致が無いことは確認している。一方、`キャッシュ・フロー` が `キャッシュ` に部分一致して誤った語を返すことが見つかった（正解は `キャッシュフロー`）。
- 閾値を使わず上位3件を人に見せる場合のRuriの命中は、70mが19/22（0.86）、310mが22/22（1.00）。

## 読み取れること

1. 表記ゆれ・言い換えは、一致検索では拾えない（0/22）。Ruriは拾える。この課題セットでは、用語を『候補として並べる』用途で効果がある。
2. 弱いのは**閾値**。devの無関係課題の1つ（`サーバー室の鍵を総務に返却します。`）が、70mで0.849、310mで0.805という高い類似度を出し、閾値がそこまで押し上げられた。70mでは、この閾値が正しい候補の多くも切り捨てた。無関係課題が10件では、閾値が不安定。
3. 310mは70mより安定して高い。ただし取得物が大きい（310mの重みは約1.2GB、70mのsnapshotは約0.29GB）。実行環境の依存（torchなど）も約0.85GBと大きい。
4. 速度は問題になりにくい。40語の用語集で、1課題あたりの中央値は70mが約0.2秒、310mが約0.5秒（`ctr_search.ruri_search` は呼び出しごとにモデルを読み込むため、その時間を含む）。
5. 再現性: 同じ入力で順位は一致した（先頭10課題×2回）。

## 限界（この結果を採否の根拠にしすぎない）

- 課題セットも正解も、Skillの設計者と同じAIが作った。独立していない。用語集は架空の40語で、実際の用語の難しさや量を表していない。
- **データの改訂**: 1回目の実行で、課題IDの接頭辞の衝突と、言い換え課題が用語集の説明文に近すぎる問題が見つかり、結果を見たあとで言い換え課題を書き直した。採否基準は変えていないが、事後の修正である。1回目の出力は [ruri-adoption-bench-run1-invalid.json](evidence/ruri-adoption-bench-run1-invalid.json) に無効として残した。
- 書き直し後の言い換え課題でも、問い合わせの2-gramの約15%が正解の文書と重なる（表記ゆれは約12%）。文面の重なりの影響は残る。
- 閾値の決め方（devの無関係課題の最大値）は、この検証のために置いた単純な規則で、最適化していない。
- 件数が少なく、区間は広い。分野・文体・用語集の規模（実際は数百語以上）への一般化は示せない。
- 310mは利用者のHugging Faceキャッシュにあった既存の取得物を読み取りだけで使った（snapshot `18b60fb8…`）。70mはリビジョン `07a8b0ab…` を一時領域へ取得した。

# 追記: 公開された実文章（日本語Wikipedia）での確認（Issue #6）

合成データの限界（作成者がAI・架空の用語集・件数が少ない）を補うため、**作成者が正解を決めない**公開された実文章で同じ比較を行った。あなた自身の業務データではない。自分のデータで回す手順は [RURI-REAL-DATA-GUIDE.md](RURI-REAL-DATA-GUIDE.md)。

## 方法（実行前に固定。`tools/fetch_wiki_bench.py` と `tools/bench_ruri_adoption.py` の冒頭）

- 用語 = 日本語Wikipediaの項目名（IT・開発・セキュリティ・データ・統計・品質・会計・契約・ネットワークなどから、私が挙げた195項目の順に、存在し条件を満たす最初の150項目）。語義 = 導入部の第1文、根拠の行 = 導入部の先頭2文
- 課題 = 項目の構造から機械的に作る。**正解は項目名・リダイレクト・本文の構造から付き、私の判断を含まない**
  - そのまま含む（verbatim）: 本文で項目名を含む最初の文 — 144件
  - 表記ゆれ・略称・英名（variant）: その項目へのリダイレクト名のうち項目名を含まないもの（最大2つ）を『◯◯について確認します。』に入れた文 — 195件
  - 言い換え（paraphrase）: 本文で項目名もリダイレクト名も含まない最初の文 — 147件
  - 無関係（negative）: 用語集に無い近い分野の項目（文房具・会議・給与など）の文で、用語集のどの項目名も含まないもの — 95件
  - dev / test は各カテゴリ内で交互に割り当て。**閾値の決定はdevだけ、報告はtest**
- 閾値の規則: devのnegativeの1位得点の**95パーセンタイル**を超えたものだけを返す。合成データでは『最大値』を使ったが、negativeが47件に増えると最大値が外れ値に引きずられるため、規則を変えた。**変更は実行前に決め、`--threshold-rule p95` として記録した**
- 採否基準は合成データと同じ（testの表記ゆれ＋言い換え n=172 で、A: Ruriの閾値つきhit@3 ≥ 0.60、B: 文字2-gramより0.15以上高い、C: testのnegative誤検出率 ≤ 0.20）
- 実行: 2026-10-17。課題セットのSHA-256 `eb7a3f09…`（Wikipediaの内容は変わるため、同じデータは再現できない。取得スクリプトの結果は変わり得る）

## 結果（test、分子/分母、95%区間はWilson）

| 方式 | そのまま含む(72)（閾値あり） | 表記ゆれ＋言い換え(172) 閾値なし | 〃 閾値あり | 無関係の誤検出(48) |
|---|---|---|---|---|
| 一致検索 | 72/72 | 0/172 | — | — |
| 文字2-gram | 55/72 | 98/172 | 49/172（0.28、0.22〜0.36） | 3/48 |
| Ruri 70m | 65/72 | 139/172（0.81） | **108/172（0.63、0.55〜0.70）** | 2/48（0.04） |
| Ruri 310m | 68/72 | 146/172（0.85） | **121/172（0.70、0.63〜0.77）** | 4/48（0.08、0.03〜0.20） |
| 一致＋Ruri 310m | 72/72 | — | 120/172（0.70） | 4/48 |

- 基準: **70m・310mとも A・B・C をすべて満たした**（『この証拠の範囲で任意の補助として推奨できる』）
- カテゴリ別（閾値あり）: 表記ゆれは70mが75/98・310mが76/98でほぼ同じ。言い換えは70mが33/74（0.45）、310mが45/74（0.61）で、**差は言い換えで出る**
- 一致検索は『そのまま含む』を全て拾い（72/72）、表記ゆれ・言い換えは0件。Ruriは閾値ありだと『そのまま含む』で3〜7件を取りこぼすため、**一致を先頭に置いてRuriで埋める併用**が合う（併用は『そのまま含む』72/72を保ち、表記ゆれ＋言い換えはRuri単独と同水準）

## 読み取れること

1. **合成データで70mが基準に届かなかった主因は、閾値の決め方だった可能性が高い**。『最大値』規則は、negative10件のうち1件の外れ値（`サーバー室の鍵…`）に閾値を押し上げられた。negativeが47件ある実文章でp95にすると、70mも基準を満たした。モデルの優劣の差と、閾値の決め方の差を分けて考える必要がある
2. 310mは70mより、言い換えで高い（閾値ありの0.61対0.45）。表記ゆれでは差が小さい。誤検出は310mがやや多い（4/48対2/48、区間は重なる）
3. 区間は広い。310mの0.70の区間（0.63〜0.77）は基準の0.60を上回るが、70mの区間（0.55〜0.70）は0.60をまたぐ
4. 速度: モデルを毎回読み込む現在の実装では、1課題あたりの中央値が70mで約1.1秒、310mで約1.7秒（この測定時は端末の負荷が高く、合成データのときより遅い）。単発のCLI呼び出しでは問題になりにくいが、大量に回すには索引・モデルの常駐が要る（Skillは常駐を設定しない）

## 限界

- 用語の選択（195項目の一覧）は私が決めた。正解の付与は機械的だが、どの分野のどの用語を並べるかには私の偏りがある。ITに寄っており、業務の固有語・社内用語は含まない
- 『言い換え』は、同じ項目の本文にある別の文を使っている。語義（導入部）と語彙が重なりやすく、実際の下書きの言い換えより易しい可能性がある（問い合わせの2-gramのうち正解の文書にも現れる割合は、言い換えで0.15、表記ゆれで0.22、そのまま含むで0.27。合成データの言い換え0.15と同水準）
- 『無関係』は百科事典の文で、業務の文面ではない。誤検出率は実際の下書きでは違い得る
- 表記ゆれは『◯◯について確認します。』という定型に入れた。リダイレクトには誤字・旧称・関連語も混じる（例: ある項目に対する別の語）。ノイズを含む実データのまま採点した
- 区間は広く、310mと70mの差を断定できない。**あなた自身の用語・文章での確認は、手順書に沿って行う必要がある**
