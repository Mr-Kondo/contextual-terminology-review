# 自動フィードバック・分散ログ設計

設計資料第3版（2026-10-17-r3）。本書は利用者が採用した設計仕様であり、実装・通信・収集を開始した記録ではない。対象Skillは `contextual-terminology-review`（用語・文脈レビュー）。

## 1. 目的と境界

実行先でレビューを記録し、許可された情報だけを改善用領域へ集め、更新案を同条件の新旧比較で評価する。対象は用語データ・検索設定・判断手順・出力形式。初期版にモデルの再学習、収集サーバー、常駐転送、他アプリの会話履歴の一括取得は含めない。

実装はClaude Code・Codex・Gemini Antigravityの共通コアと、各実行経路の最小の接続処理で行う。Work/Coworkも独立して動作確認する。Skill配置だけで実行監視・記録が自動的に有効になったとは扱わない。ホストのフック機能や履歴形式は仮定せず、実装時に公式仕様と実動作を確認する。

既定の自動化は、実行記録、自動検査、フィードバック集計、更新案作成、新旧比較、ローカル書き出しまで。共通基準への反映は、利用者の明示的な採用判断に従う。ログ中の文章やAI採点を、規則の変更命令・採用承認とみなさない。

## 2. 六つの処理段階

| 段階 | 含むもの／含まないもの | 主な出力 |
|---|---|---|
| 記録 | 実行条件・入出力・失敗／正誤判断は別 | 実行記録 |
| 検出 | 引用不備や意味変更の候補／原因の確定は別 | 自動検査・AI疑義 |
| 確認 | 意図・根拠・原因の人手確認／採用は別 | 確認済み・保留・問題なし |
| 更新案 | 辞書・検索・手順・説明の差分／本番反映は別 | 適用範囲付き候補 |
| 比較評価 | 同条件での現行版・候補版の比較／承認は別 | 改善・悪化・不明 |
| 反映・監視 | 採用・保留・復元／評価基準の恣意的変更は別 | 版・判断履歴 |

これは処理段階による分類である。分野・重大度・原因・案件・相手・媒体は独立したタグとし、複数の原因がある場合は複数記録する。原因不明を無理に分類しない。

## 3. 保存領域と配置

次の名称は設定項目であり、実装時に明示された絶対パスへ解決する。実際のPCパス・リモート接続先・共有先はまだ未指定。利用開始時に保存場所と許可範囲を提示する。外部送信先は未設定を既定とする。

| 設定 | 内容と権限 |
|---|---|
| `runtime_data_root` | 各実行先の、案件で保存を許可された永続領域。実行・参照・フィードバックを保持 |
| `improvement_root` | 本人または承認された管理者の改善用領域。許可済み記録、更新案、比較、採否を保持 |
| `skill_source_root` | Skill本体と公開可能なテスト・一般規則の開発領域。実業務ログを含めない |
| `evaluation_gold_root` | 採点理由・未使用例。レビューを生成・改善するAgentからアクセスを分離 |

```text
runtime_data_root/
  runs/YYYY-MM/<run_id>/
    run.json                  開始条件・保存方針（終了で上書きしない）
    events/<event_id>.json     完了・失敗・自動検査等の追記イベント
    feedback/<event_id>.json   人の確認・訂正の追記イベント
    private/                  個別に保存を許可した入力・出力・抜粋
  outbox/<package_id>/        exportで検査した移送用パッケージ
improvement_root/
  inbox/<package_id>/         取り込み済みの共有可能記録
  quarantine/                 不明形式・競合等（原文をエラー表示へ漏らさない）
  proposals/                  未採用の更新差分
  evaluations/                新旧比較と試験条件（未使用例の正解は置かない）
  decisions/                  採否・版・理由・復元記録
```

スキルのインストール先、公開リポジトリ、自動同期が未承認のフォルダを業務ログの既定保存先にしない。設定例・公開テストに実パス・ユーザー名・案件名を含めない。作業リポジトリの除外設定だけを機密保護としない。

初期の保存形式は実行・イベントごとのUTF-8 JSONと必要な添付。共有された一つのJSON/JSONLやSQLiteへ複数ホストが直接同時書き込みしない。集計索引は再生成可能な派生データとする。初期はPython標準ライブラリと既存のPydantic等を優先し、新たなDB・Webサービスを必須にしない。

## 4. 実行と記録の契約

共通管理スクリプトの操作は `record`、`feedback`、`check`、`export`、`import`、`propose`、`evaluate` とする。ファイル数は固定しない。`record` は開始・終了・失敗を扱い、`feedback` は対象の実行ID／指摘IDに結び付ける。従来の導入・更新・削除スクリプトとは責務を分ける。

1. レビュー開始前に実行IDを作成し、保存方針と版を記録する。
2. 根拠参照と出力を実行IDへ結び付ける。永続保存を許可されていない原文をログのために複製しない。
3. 完了または失敗のイベントを保存する。書き込みは同一ファイルシステム内の一時ファイルと原子的置換等、標準的な方法で行い、部分ファイルを成功扱いにしない。既存IDを上書きしない。
4. 開始後に終了イベントのない実行は未完了・中断疑いとする。処理中との区別を付け、終了理由を推測しない。
5. 書き込み不能の場合は記録失敗を明示する。レビュー継続が許可される場合も「保存未確認」と表示し、記録済み件数へ加算しない。秘密の代替フォルダへ自動退避しない。

各環境の正規の入口から、この記録処理を通す。AIが文章で「保存した」と答えただけでは成功とせず、実ファイルまたは保存機能の応答と再読込を確認する。入口を迂回した利用は観測できないため、全使用回数を把握したとは報告しない。

## 5. 記録スキーマの必須項目

| 区分 | 必須の情報 |
|---|---|
| 来歴 | `schema_version`、`run_id`、`event_id`、作成日時（UTC）、元イベント／訂正対象ID、パッケージID |
| 実行条件 | 案件の不透明ID、実行環境、実際に取得できたモデル識別子、Skill・用語データ・索引・設定・検査器の版 |
| レビュー | 対象表現、指摘ID、修正案、相手・媒体、適用範囲。原文非保存なら参照IDと非保存理由 |
| 根拠 | 資料ID・版・使用位置・短い使用箇所・引用／要約／推論の区別、参照検証・意味適合の別状態 |
| 評価 | 機械検査、AIの疑義、人の確認、採否を別フィールド。評価者・日時・理由・証拠 |
| 保存条件 | 所有案件、許可された保存範囲・共有範囲、保存期限／確認待ち、原文保存の可否、削除対象への依存参照 |

取得不能のモデル版等は `unknown` と理由を残し、現在値を後から埋めて取得済みにしない。非保存の原文を推測して埋めない。絶対パス・抜粋・個人識別子・ハッシュも機微情報になり得るため、外へ出せる項目とは限らない。

人のフィードバックの最小入力は次の四項目＋任意理由とする。訂正は元記録を消さず、訂正イベントから参照する。集計時は有効な最新版を使い、訂正を独立例へ水増ししない。

- 指摘：妥当／不適切／不明。
- 本人の意図：保持／変わった／不明。
- 使用：そのまま／修正して／不使用。
- 受け手との確認：確認できた／食い違った／未確認。理解を実測したと言うには、別途質問・回答・必要項目の採点を残す。

未回答を肯定にしない。使用されたことを正確性・伝達成功・人による検証と同一視しない。本人の好み、合意不足、誤用、未確認を区別する。

## 6. 別PC・リモート・他利用者からの収集

| 利用場所 | 記録と収集 |
|---|---|
| 同じPCの別案件 | 案件別領域に記録し、共有許可のある項目だけ集約する |
| 本人の別PC | そのPCに保存。exportしたパッケージを許可された経路で移し、importする |
| 一時的なリモート環境 | 永続保存先と終了前の書き出しを事前確認。確保できなければ消失リスクと記録不能を明示する |
| 他の利用者 | 利用者の領域で記録し、提供を許可した記録だけ受け取る。インストールを送信同意と解釈しない |
| 実行・保存できない経路 | 定型記録の手動保存・取り込みを案内。できなければ未収集とし、自動記録済みと言わない |

初期のexport/importはファイル方式で、ネットワーク転送を行わない。送信先・経路・項目・頻度・権限が承認された場合だけ、後続版で転送機能を追加する。スケジュール実行・常駐サービスは別途の明示的な依頼なしに設定しない。

exportは既定で、実行の成否、版、問題種別、検査結果等の許可された項目だけを対象とする。入力全文、出力全文、引用原文、添付、絶対パス、氏名・案件名は除外する。匿名化処理だけで共有可と判定しない。項目別許可が未設定なら共有用書き出しを停止し、確認待ちを示す。受け手の回答と評価用の正解も既定で含めない。出力文や引用に原文が残るため、privateフォルダを除くだけでは不十分である。

各パッケージはスキーマ版、生成元の不透明ID、実行・イベントID、項目一覧、共有範囲、許可状態、ファイルハッシュ、内容のバイト数を持つmanifestを添える。ハッシュは移送中の同一性の検査であり、送信者の認証や内容の正しさを証明しない。受領者は提供元と共有先が許可範囲内か確認する。

importは一時領域で形式・ハッシュ・許可項目・サイズ上限・パス境界を検査してから確定する。未知スキーマ、絶対パス・親への移動・リンク経由の境界外参照、上限超過、ハッシュ不一致を拒否する。添付はデータとして扱い、内容の命令・コードを実行しない。エラーに原文を表示しない。

同じイベントID・同じ内容の再取り込みは成功済みとして重複加算しない。同じID・異なる内容は競合として隔離し、先勝ち／後勝ちで上書きしない。異なるIDでも同一案件・元課題の反復やパラフレーズはグループIDで関連付ける。原文が非共有で判定できない重複は不明と残す。import後もoutboxを自動削除せず、受領記録と保存方針に従う。

## 7. 原因別の更新と採用条件

| 確認した原因 | 更新対象 |
|---|---|
| 定義・適用範囲が不足 | 根拠付きの用語データ、案件限定語義 |
| 適切な資料を検索できない | 別名、クエリ、分割、検索設定 |
| 正しい資料を参照したが判断を誤る | 判断手順と回帰例 |
| 専門的には正しいが相手に伝わらない | 相手・媒体別の補足や口頭修復例 |
| 責任・成果物が未合意 | 確認事項。一般用語の定義を変更しない |

`propose`は根拠、確認状態、対象案件・分野、変更差分、想定する直前の版、保持条件・禁止変更、評価計画を持つ。未確認の指摘は仮説のまま候補化できるが、確定誤用の回帰例や一般規則に自動昇格しない。

`evaluate`は、現行版と候補版に同じ入力・原資料・参照可能範囲・モデル・生成設定・採点条件を与える。順序や反復数を記録し、モデル・資料版の違いがあれば交絡として別試験にする。失敗回帰例、正しく処理できていた例、修正不要例を含める。独立した未使用評価は別の評価担当・権限領域で実施し、改善するAgentには正解も未使用入力も渡さない。その評価結果から調整に使った例は以降未使用ではない。

既知例の改善と、確認範囲で新たな重大な意味変更がないことを別に示す。意味保持の不合格・保留を読みやすさの点数で相殺しない。未使用評価が未実施なら「未実施」とし、回帰検査のみの状態と区別する。公開開発例の合格を実務性能の証明にしない。

反映時は、人の明示的な採用、対象範囲、根拠、比較結果、直前の版、変更ハッシュを照合する。評価後に基準が変わった場合は競合として再確認する。Skill・用語・索引の版を分離し、索引更新の失敗を残す。旧版への復元も判断イベントにし、履歴を改変しない。初期版で本番の自動採用はしない。

## 8. 集計・週30分の運用

自動収集した全記録、共有された記録、人が確認した記録を母集団として区別する。利用総数が未知なら収集率を算出しない。指摘例だけでなく、指摘なし・問題なしの例も、記録した抽出条件とseedで確認候補に選ぶ。高リスク優先抽出と無作為抽出は別集計にする。抽出候補の残りを正しいとみなさない。

| 指標 | 分子／分母と解釈 |
|---|---|
| 引用不備 | 機械検査で不備があった参照／検査した参照。意味適合とは別 |
| 不要な修正 | 不要と人が確認した修正／人が確認した修正 |
| 有害な意味変更 | 意図・責務・条件を損なった案／人が検証した案 |
| 確認済み問題の再発 | 再発した機会／同じ判断が必要だった確認対象の機会 |
| 受け手の理解 | 正しく説明できた必須項目／評価計画で定めた必須項目。未回答項目を落として分母を縮めない |
| 負担 | 記録・確認・根拠確認・比較・練習・初期整理の本人時間。協力者時間は別 |

既存02の「指摘の適合」「修正不要課題に対する不要指摘」等とは指標IDと分母を分ける。件数、独立課題数、保留、欠測、適用外を表示する。分母0は未評価。環境・案件・分野別に集計し、繰り返しを独立例数にしない。AI評価を人手評価へ混ぜず、人との一致・不一致・未確認を別集計にする。利用者の採用率を正確性の指標にしない。

毎回は四項目の任意入力、週次は自動生成した確認一覧と比較結果を使う。本人の時間は合計週30分程度、協力者は別。初期配分は記録5分、根拠確認15分、比較5分、練習・更新5分とし、日々の入力と初期設定もこの負担へ計上する。固定件数・全分野の毎週確認は強制しない。超過時は確認数を減らして保留を残し、自動採用で埋め合わせない。

## 9. 保存期限・削除・導入更新削除

原文の永続保存は明示的に許可されたときだけ有効にする。保存期限・共有範囲が未決の原文は複製せず、最小メタデータで運用できる場合に限り記録する。メタデータの保存先・保存方針も未承認なら記録失敗を明示する。原文保存なしの実行は再現できる範囲が限定されることを表示する。自動削除日数は根拠なく設定しない。

資料・実行・イベント・パッケージ・索引・回帰例の依存IDを持ち、削除対象から派生先を追えるようにする。削除時は抽出文、出力内引用、索引、outbox、inbox、回帰例、バックアップの管理対象複製を確認する。権限外の共有先やバックアップは削除依頼・確認待ちとして残し、全消去完了と言わない。削除済みIDだけの最小台帳で、古いパッケージ再取り込み時の復活を防ぐ。再提供が必要な場合は新たな明示的判断を要する。

Skillの更新・アンインストールはログを既定で保持する。データ削除は対象・範囲・複製先を表示する別操作とし、通常のアンインストールや開発後の片付けで原資料・用語正本・評価履歴を削除しない。機密の削除要請と、履歴の通常の追記原則は区別する。

## 10. 実装・受入の段階

1. 共通の記録・追記・失敗表示を実装し、仮の保存先で検査する。
2. ローカルexport/import、重複・競合・拒否、手動保存経路を検査する。
3. 集計、原因別候補、新旧比較、明示的採用・復元を検査する。
4. 各ホスト・利用経路で実記録と再読込を確認する。不能な経路は未実施とする。
5. 収集量と確認負担を測り、必要な場合に限り承認済み転送の後続設計を行う。

初期段階でサーバーや常駐処理を作らないことで保守負担を抑える。その代わり、別PCからの移送には操作が残り、提供されない利用の状況は分からない。設計の完成、仮環境の自動検査、各ホストの実動作、実務の改善をそれぞれ独立して報告する。

## 11. 具体例

別PCで「取りまとめ」を単なる資料集約と解釈した。本人が主担当の意図だったと確認し、元の環境に根拠と回答を保存する。共有許可がある一般化記録だけを管理者へ移す。一般化で責任範囲を変えていないか本人が確認する。資料を共有できない場合は権限のある元環境で比較し、許可された結果だけを戻す。

更新は当該案件の語義または判断手順とし、資料集約だけを意味する別例で過剰修正がないか確かめる。元資料が見られなければ、一般化例の合格と原案件の確認状態を分ける。「引渡し」も未リリースだけを根拠に部分引渡しへ自動変換しない。
