# E2E評価（初見の課題で、Skillありとなしの最終出力を比べる）

[効果測定](EFFECT-MEASUREMENT.md)の予備試験は、用意した修正案を受け手に渡すもので、**Skillが初見の入力から適切な案を作れるか**は見ていない。ここは、同じ入力・同じ資料で、Skillありと素のモデルを比べた測定。**人の受け手の理解は測らない**。測るのは、最終出力の判定と修正案の語句。

## 方法

- 課題集 `tools/data/e2e-cases.json`（32件、すべて架空）。dev・test に、種類ごと4件ずつ:
  - **misuse**（誤用）: 資料の定義に照らして誤っている（例: 冪等、精度/確度、ハッシュ化/暗号化、検収）
  - **ambiguity**（曖昧）: 誤用とは言えないが意味が定まらず、資料も決め手にならない（例: 『取りまとめます』『バックアップは取得済みです』『障害は対応済みです』）。期待は『保留』で、責務や完了状態を作らないこと
  - **correct**（修正不要）: 資料に合う正しい用法。直さないこと
  - **mismatch**（資料の取り違え）: 資料が別案件・旧版・草案・他社のもの。この文に当てはめず保留すること
- 実行 `tools/e2e_eval.py`: 各課題を `claude -p` に1件ずつ渡す。資料は `sources/` のファイルで渡す。**違いはSkillの有無だけ**。
  - baseline: Skillなし（`--disable-slash-commands`）
  - skill: 作業ツリーのSkill（v0.1.3）だけを置く。依頼文でSkill名を指す
  - どちらも、実環境の他のSkill・フック・CLAUDE.md は読まない。最後に、判定（misuse / ambiguous / ok / insufficient）と修正案をJSONで付ける追加指示を、同じ文面で与えた
- 採点は機械的。misuse は『misuse と判定し、修正案に正しい語句がある』、ambiguity と mismatch は『ambiguous か insufficient と判定し、misuse と言わない』、correct は『対象語についての指摘が全て ok』。責務や完了状態の無断追加は、課題ごとの禁止語句で数える
- 基準（結果を見る前に固定）: 全体の正答率の差（skill − baseline）が **+0.10 以上、かつ改善した課題数 > 悪化した課題数**。correct の誤指摘が baseline より +0.10 を超えて増えない。無断追加が baseline より増えない。Skillを直してよいのは dev だけ。test は1回だけ測る
- 各課題2回ずつ実行（1課題×1条件につき2回）

## 結果

| | baseline（Skillなし） | skill（v0.1.3） |
|---|---|---|
| **dev**（16課題×2回） | 25/32 | **30/32** |
| **test**（16課題×2回、1回だけ測定） | 26/32 | **30/32** |
| 合算（64回） | 51/64 = 0.80（0.68〜0.88） | **60/64 = 0.94**（0.85〜0.98） |

| 種類（合算、各16回） | baseline | skill |
|---|---|---|
| misuse（誤用を見つけ、正しい語句で直す） | 16 | 16 |
| ambiguity（保留する） | 12 | **16** |
| correct（直さない） | 9 | **13** |
| mismatch（別の資料を当てはめず保留する） | 14 | 15 |

| 基準（test） | 結果 |
|---|---|
| 正答率の差 +0.10 以上、改善 > 悪化 | **満たす**（差 +0.125、改善4・悪化1・変化なし11） |
| correct の誤指摘の増加が +0.10 以内 | 満たす（baseline 3/8、skill 1/8） |
| 無断追加が baseline より増えない | 満たす（どちらも0。ただし検出力は低い） |

合算の符号検定は、改善8・悪化2で p = 0.11。**統計的に有意とは言えない**。

そのほかの数値（合算）:

| | baseline | skill |
|---|---|---|
| correct で、対象語以外も含めて何かを指摘した（厳しい数え方） | 16/16 | 14/16 |
| correct での、対象語以外への指摘の件数 | 21 | 16 |
| 修正案の長さ（原文に対する比の中央値） | 3.4 | 3.3 |
| 1回あたりの時間 | 14.9秒 | 20.7秒 |
| 1回あたりの費用 | 約0.04ドル | 約0.08ドル |
| Skillが呼ばれた回数 | — | 64/64（名前を指したため） |

## 読み取れること

- **誤用の検出は差がない**（16/16 対 16/16）。資料に定義があれば、素のモデルでも見つけて正しく直す。Skillの強みは検出ではない
- **差が出たのは『保留の仕方』**: 資料が決め手にならない文で、素のモデルは判定が揺れた（12/16）。Skillありは全て保留できた（16/16）。正しい用法を直さない点でも、Skillありの方が誤指摘が少ない（9→13）
- 差は小さく、有意ではない。課題は32件、2回ずつで、区間は広い
- **費用は約2倍**（時間は約1.4倍）。差を取るために払うもの
- どちらも修正案が長い（原文の3倍強）。Skillは短くしない。実務で貼る文には長いかもしれない

## 採点の不備と、事後の感度分析（正直な記録）

- **採点コードの食い違い**: correct の初版の採点が、課題集の規則（対象語についての指摘が全て ok）と違い、**全ての指摘**を対象にしていた。dev の結果を見て、規則どおりに直した（厳しい数え方は上の『何かを指摘した』に残してある）。直す前は、dev で baseline 21/32、skill 26/32 だった。直した後に test を測った
- **対象語の文字列一致への依存**: ambiguity と mismatch は、指摘の対象の文字列が課題の対象語を含むものを見る。モデルが保留を別の語句（例: X8 の『3重』）に付けると、保留しているのに不合格になる。これは採点の不備で、Skill側の失敗ではない。事後の感度分析として、全ての指摘を見る数え方も出した（baseline 51/64、skill 61/64。結論は変わらない）。test の事前の基準は、事前の採点で判定した
- Skillありが落とした4件: C2（正しい用法に『標準偏差か範囲か』を確認として指摘）、C3（対象語を含む指摘が『ハッシュ化の方式の記載がない』）、C6（『金曜です』を予定か確定か曖昧と指摘）、X8（上記の採点の不備）。C2・C3・C6 は、対象語そのものでなく付随する点への指摘で、厳しすぎる採点とも言える

## 限界

- **素のモデルが弱い比較ではない**: baseline にも、判定の種類（ambiguous、insufficient）と資料の読み方を、追加指示で与えた。何も指示のない素のモデルより、baseline は有利
- 課題・資料・禁止語句の作成者は、Skillの設計者と同じAI（独立していない）。禁止語句は特定の言い回ししか拾わず、**無断追加の検出力は低い**（どちらも0件は『無断追加がない』の証拠にならない）
- 修正案の質（意味を保っているか、自然か）は見ていない。誤用の修正が『正しい語句を含む』かで近似している。言い換えは取りこぼす
- Skill名を指して呼んだ。自然な依頼で選ばれるかは [TRIGGER-EVAL](TRIGGER-EVAL.md)（実環境では約7割）
- Claude Code の既定モデルのみ。Codex・Antigravity は未測定。課題は1文で、実務の長い資料・複数の指摘・複数ターンは扱っていない
- **人の受け手の理解は、この評価では測っていない**

## 再現

```bash
python3 tools/e2e_eval.py validate
python3 tools/e2e_eval.py run --split test --runs 2 --out .work/e2e-test.json     # 要 claude CLI。1回あたり十数〜数十秒
python3 tools/e2e_eval.py score --results .work/e2e-test.json --split test
```

生データ（各実行の最終JSON・時間・費用）は [docs/evidence/e2e/](evidence/e2e/)。
